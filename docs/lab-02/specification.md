# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a Requester-facing ticketing MVP: a Requester, selected through a temporary
Development Requester context, can create an IT support ticket with supporting
attachments, receive a system-generated Ticket Number, and then find, open, and
manage that ticket — search, filter, sort, and page through My Tickets, inspect
Ticket Detail, and add or soft-remove attachments — with ownership strictly
enforced so one Requester can never see or touch another Requester's data.

## 2. Stakeholder Request Interpretation

IT wants a self-service front door for support requests. A Requester describes a
problem, classifies it (category, related system, priority), attaches evidence,
and submits. The system must hand back an official ticket number, let the
Requester find that ticket again later among all their others, and let them manage
its attachments — without ever exposing another Requester's tickets. Because real
login isn't built yet, a "pick a test identity" screen stands in for authentication
this sprint only, and is explicitly labeled as such everywhere it appears.

## 3. Scope

### Included

- Development Requester Selection screen (active Requesters only) and Change
  Requester action.
- Create Ticket: category, related system, requested priority, summary,
  description, up to 5 attachments; server-generated Ticket Number.
- My Tickets: search, filter, sort, pagination, empty state, no-results state.
- Requester Ticket Detail: read-only ticket fields, attachment list.
- Attachment lifecycle: add, download/preview, soft-remove with optional reason.
- Ownership enforcement on every ticket and attachment operation.
- Idempotent ticket creation (duplicate-submission protection).
- Zen Green application shell and reusable form/list/badge/state components.

### Excluded

- Authentication, sessions, passwords, real role-based authorization.
- IT Staff dashboard/queue, ticket claiming/reassignment, **IT Priority**, and
  **Ticket Owner** — neither field is stored or displayed anywhere in Lab 2,
  since nothing in this sprint sets or owns them (see §11).
- Public Comments, Internal Notes, Actions Taken.
- Any status transition beyond the initial `NEW` status.
- Administration of users, Requesters, roles, or reference data.

## 4. Functional Requirements

- FR-01 The Requester selects a Development Requester from the active list before
  any ticket screen is reachable.
- FR-02 The Requester creates a Ticket with category, related system, requested
  priority, summary, description, and up to 5 attachments in one submission.
- FR-03 The system generates and returns a unique Ticket Number on successful
  creation.
- FR-04 The Requester views a paginated list of only their own Tickets.
- FR-05 The Requester searches their Tickets by ticket number or summary text.
- FR-06 The Requester filters their Tickets by Category, Requested Priority, and
  Current Status.
- FR-07 The Requester sorts their Ticket list by Created Date, Summary, Requested
  Priority, or Current Status.
- FR-08 The Requester opens a Ticket Detail screen showing full read-only ticket
  information and its attachment list.
- FR-09 The Requester adds a new attachment to an existing owned Ticket.
- FR-10 The Requester downloads or previews an active attachment.
- FR-11 The Requester soft-removes an owned, active attachment with an optional
  reason.
- FR-12 The Requester switches the active Requester context, which reloads all
  requester-scoped data from the new identity.
- FR-13 The system prevents a retried or double-submitted Create Ticket request
  from creating a second Ticket.
- FR-14 The system enforces Requester ownership on every Ticket and Attachment
  read or write.

## 5. Business Rules

- BR-01 The official Ticket Number is generated by the backend, is unique, and
  follows the format `TKT-YYYY-NNNNNN` (year of creation, zero-padded sequence);
  the generation mechanism is specified in BR-38.
- BR-02 A new Ticket begins with Current Status `NEW`.
- BR-03 Lab 2 uses a Development Requester selector instead of login. The selected
  identity is for testing only and is not authentication.
- BR-04 A Ticket's Requester is fixed to the currently selected Development
  Requester at creation time; the client cannot set or override it.
- BR-05 Only active RequesterUsers are returned by the active-Requesters endpoint
  and appear in the selector dropdown.
- BR-06 An inactive Requester's existing Tickets remain in the database but that
  Requester cannot be selected as the acting context.
- BR-07 The selected Requester is stored in `sessionStorage`; a new tab or browser
  restart requires reselecting.
- BR-08 Changing Requester replaces the requester context and forces My Tickets
  and Ticket Detail data to be refetched; no previously loaded ticket data from
  the prior Requester is retained in the UI after switching.
- BR-09 A Ticket belongs to exactly one RequesterUser; ownership is checked on
  every read or write of that Ticket and its Attachments.
- BR-10 A request for a Ticket or Attachment owned by a different Requester
  returns 404, identical to a request for a nonexistent resource.
- BR-11 `POST /api/tickets` requires a client-generated `Idempotency-Key` header
  (UUID). A repeated request with a key already used by that Requester returns
  the original Ticket instead of creating a duplicate.
- BR-12 Idempotency keys are scoped per Requester and enforced by a unique
  constraint on (`requesterId`, `idempotencyKey`).
- BR-13 The Submit button is disabled immediately on click and re-enabled only
  after the request resolves, as a first line of defense alongside BR-11/BR-12.
- BR-14 Ticket Summary and Description are trimmed server-side before validation
  and storage.
- BR-15 Ticket Summary is required, 5–120 characters after trimming.
- BR-16 Description is required, 10–2000 characters after trimming.
- BR-17 Category and Related System are required and must reference a currently
  active row; a reference to an inactive or removed row is rejected.
- BR-18 Requested Priority is required; allowed values are `LOW`, `MEDIUM`,
  `HIGH`; the UI pre-selects `MEDIUM`.
- BR-19 On any validation failure, no Ticket is created and the Requester's
  already-entered field values and selected attachments are preserved in the form.
- BR-20 If Ticket creation succeeds but a subsequent attachment upload fails, the
  Ticket is retained; the failure is reported with a retry option from Ticket
  Detail rather than discarding the Ticket.
- BR-21 Search matches Ticket Number by prefix or Summary by case-insensitive
  substring.
- BR-22 The Ticket list can be filtered by Category, Requested Priority, and
  Current Status.
- BR-23 The Ticket list can be sorted by Created Date, Summary, Requested
  Priority, or Current Status; the default sort is Created Date descending with
  Ticket id descending as a tiebreaker.
- BR-24 Pagination is 1-based; default page size is 10; allowed page sizes are
  10, 20, 50; a page beyond the last available page returns an empty result set,
  not an error.
- BR-25 An empty list (the Requester owns zero Tickets) is presented differently
  from a no-results result (the Requester owns Tickets, but none match the
  current search/filter).
- BR-26 Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF.
- BR-27 Maximum attachment size is 5 MB per file.
- BR-28 Maximum 5 **active** attachments per Ticket; soft-removed attachments do
  not count toward this limit.
- BR-29 An upload request containing more than 5 files is rejected wholesale
  (409); none of the files in that request are stored.
- BR-30 An upload request is validated and stored atomically: if any file in the
  batch fails the type, size, or active-count check, none of the files in that
  batch are stored.
- BR-31 Attachment removal is soft: the row is retained with `removedAt` and an
  optional `removalReason` set; the underlying file is not deleted from storage.
- BR-32 A removed Attachment cannot be downloaded or previewed by anyone; its
  metadata (filename, size, upload date, removal date, and reason if provided)
  remains visible on Ticket Detail.
- BR-33 Only the owning Requester may add or remove an Attachment on their own
  Ticket.
- BR-34 Removing an Attachment requires an explicit confirmation step; the
  removal reason is optional free text up to 200 characters.
- BR-35 Previewing an active Attachment opens the stored file directly in a new
  browser tab; no in-app thumbnail or embedded preview is rendered.
- BR-36 Ticket Detail is retrievable only by the owning Requester; a Ticket owned
  by another Requester and a nonexistent Ticket both return 404, indistinguishable
  to the caller.
- BR-37 Lab 2's Requester context (selector plus `X-Requester-Id` header) is a
  temporary substitute for authentication with no cryptographic identity
  guarantee. Lab 3 replaces it with real session-based authentication without
  changing the Ticket/Attachment ownership model defined here.
- BR-38 Ticket Numbers are generated by computing a candidate `TKT-YYYY-NNNNNN`
  from the count of Tickets created so far this year, attempting the insert, and
  retrying (bounded to 5 attempts) on a unique-constraint violation of
  `ticketNumber`, rather than reading `MAX(id)+1`, which is not concurrency-safe
  under simultaneous creates. A dedicated per-year Postgres sequence was
  considered but rejected: it requires either pre-provisioning a new sequence
  object every year or issuing raw DDL at insert time, which is more operational
  complexity than a bounded insert-and-retry loop needs for this app's actual
  concurrency (one Requester at a time in dev/testing use).
- BR-39 Adding or soft-removing an Attachment updates the parent Ticket's
  `updatedAt` timestamp; this is the value the My Tickets "Last Updated" column
  displays, so attaching or removing evidence is reflected there even when no
  Ticket field itself changed.

## 6. UI Specification Summary

Full detail is deferred to `ui-spec.md`; this section fixes the structure that
document must follow.

- **Application shell**: TokTickIT identity, My Tickets / Create Ticket nav,
  current Requester name with a Change Requester action, active-page indication,
  responsive mobile nav — per Zen Green tokens (labsheet §7).
- **Development Requester Selection**: dropdown of active Requesters only,
  Continue action, loading/empty/API-failure states, keyboard accessible.
- **Create Ticket**: system-generated/read-only values visually distinct from
  editable ones; Summary and Description given the most width; Attachments below
  the main fields; Submit shows a busy state and is disabled while pending
  (BR-13); validation messages render beside their field, never only at the top.
- **My Tickets**: search box, Category/Requested Priority/Current Status filters,
  sortable columns, pagination controls, Create Ticket action; desktop table
  collapses to stacked cards below 768px (no horizontal page scroll); distinct
  empty vs. no-results states (BR-25).
- **Ticket Detail**: read-only header fields grouped separately from the
  Attachments panel; active attachments show filename/size/date with
  Preview/Download/Remove actions; removed attachments show the same metadata
  with no action controls, visually muted.
- **Badges**: Requested Priority and Current Status use distinct, non-color-only
  indicators, defined precisely in `ui-spec.md`.
- Neither **IT Priority** nor **Ticket Owner** appears on any screen (§3).

## 7. Data Changes

### Models

- **RequesterUser** — `id`, `name`, `email` (unique), `isActive` (default
  `true`), `createdAt`.
- **RelatedSystem** — `id`, `name` (unique), `isActive` (default `true`),
  `createdAt`. Mirrors the existing `Category` shape.
- **Category** — unchanged from Lab 1.
- **Ticket** — `id`, `ticketNumber` (unique), `requesterId` (FK →
  RequesterUser), `categoryId` (FK → Category), `relatedSystemId` (FK →
  RelatedSystem), `summary`, `description`, `requestedPriority`
  (`Priority` enum: `LOW`/`MEDIUM`/`HIGH`), `status` (`TicketStatus` enum),
  `idempotencyKey` (uuid), `createdAt`, `updatedAt`.
- **Attachment** — `id`, `ticketId` (FK → Ticket), `originalFilename`,
  `storedFilename`, `mimeType`, `sizeBytes`, `createdAt`, `removedAt`
  (nullable), `removalReason` (nullable).

### Enums

- `Priority`: `LOW`, `MEDIUM`, `HIGH`.
- `TicketStatus`: `NEW` only. **Decision**: the enum is intentionally scoped to
  the single value Lab 2 can produce, not pre-populated with future statuses.
  **Schema evolution for Lab 3**: additional values (`OPEN`, `IN_PROGRESS`,
  `RESOLVED`, etc.) are added by a Lab 3 migration when the IT Staff workflow
  introduces status transitions; no Lab 2 code depends on the enum staying
  single-valued.

### Relationships

- One RequesterUser → many Tickets; one Ticket → one RequesterUser.
- One Category → many Tickets; one RelatedSystem → many Tickets.
- One Ticket → many Attachments.

### Indexes and constraints

- `Ticket.ticketNumber` unique.
- `Ticket.requesterId` indexed (every list query filters by it).
- `Ticket.createdAt` indexed (default sort).
- Unique constraint on (`Ticket.requesterId`, `Ticket.idempotencyKey`) — enforces
  BR-11/BR-12 at the database level, not just in application code.
- `RequesterUser.email` unique.
- `RelatedSystem.name` unique.
- `Attachment.ticketId` indexed.

### Migration plan

- `RequesterUser` and `RelatedSystem` ship in their own migrations, tied to
  their respective Issues.
- **Decision**: `Ticket` and `Attachment` ship in one shared migration, since
  they are introduced by the same Create-Ticket Issue and Attachment has a
  hard foreign-key dependency on Ticket that has no independent meaning.

### Seed data

Beyond the Lab 2 minimums (4 categories, ≥6 related systems, ≥4 active
Requesters, ≥1 inactive Requester), the seed also creates demonstrable ticket
volume, re-runnable without duplication:

- ~25 Tickets for one active Requester (proves pagination, search, sort,
  filter against a non-trivial set).
- ~5 Tickets for a second active Requester (proves cross-Requester isolation
  with a small, easily-inspected set).
- 0 Tickets for a third active Requester (proves the empty-state UI).
- A mix of Categories, Related Systems, and Priorities across the seeded
  Tickets so filter/sort combinations are actually exercised.

## 8. API Contract

All Ticket/Attachment endpoints require an `X-Requester-Id` header identifying
the acting Development Requester (§11). Missing or non-integer values return
400. A value that does not match an active Requester returns 403 (the
Requester exists but is not currently valid, distinct from the 404s below).

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/categories` | Active Categories (existing, Lab 1) |
| GET | `/api/related-systems` | Active Related Systems |
| GET | `/api/requesters` | Active Development Requesters |
| POST | `/api/tickets` | Create a Ticket |
| GET | `/api/tickets` | Paginated, searchable, filterable, sortable list of the caller's own Tickets |
| GET | `/api/tickets/:id` | One owned Ticket, with its Attachments |
| POST | `/api/tickets/:id/attachments` | Upload up to 5 files at once |
| GET | `/api/tickets/:ticketId/attachments/:attachmentId` | Attachment metadata |
| GET | `/api/tickets/:ticketId/attachments/:attachmentId/download` | Stream an active Attachment's file (also used as "preview", BR-35) |
| DELETE | `/api/tickets/:ticketId/attachments/:attachmentId` | Soft-remove an Attachment |

**POST /api/tickets**
Headers: `X-Requester-Id`, `Idempotency-Key` (uuid).
Body: `{ categoryId, relatedSystemId, summary, description, requestedPriority }`.
- 201 — created: `{ id, ticketNumber, requesterId, categoryId, relatedSystemId, summary, description, requestedPriority, status, createdAt, updatedAt }`.
- 200 — replay of a previously used `Idempotency-Key`: same shape, no new row created (BR-11).
- 400 — missing/invalid field, or `categoryId`/`relatedSystemId` not active: `{ errors: [{ field, message }] }`.

**GET /api/tickets**
Query: `search`, `category`, `requestedPriority`, `status`, `sortBy`
(`createdAt`|`summary`|`requestedPriority`|`status`), `sortDir` (`asc`|`desc`),
`page`, `pageSize` (10|20|50).
- 200 — `{ data: Ticket[], page, pageSize, totalCount, totalPages }`. Out-of-range
  `page`/`pageSize` values are clamped, not rejected.
- 400 — invalid `sortBy`, `sortDir`, `requestedPriority`, or `status` value.

**GET /api/tickets/:id**
- 200 — Ticket fields plus `attachments: Attachment[]` (each including
  `isRemoved`, `removedAt`, `removalReason`).
- 404 — not found, or owned by a different Requester.

**POST /api/tickets/:id/attachments**
`multipart/form-data`, field `files` (1–5 entries).
- 201 — array of created Attachment metadata.
- 400 — malformed request only: the `files` field is missing/empty, or `:id` is
  not a valid Ticket-id format. Checked before any file-content validation, since
  a malformed request cannot be counted or inspected.
- 409 — more than 5 files in the request (BR-29), or accepting the batch would
  push the Ticket's active-attachment count above 5. Checked first among the
  content-validation codes below, because a count failure makes per-file checks
  moot.
- 415 — the first file, in submission order, whose type is not
  JPG/JPEG/PNG/WEBP/PDF. Checked second.
- 413 — the first file, in submission order, that exceeds 5 MB. Checked third,
  only once no file has already failed the 409 or 415 checks above.
- 404 — Ticket not found or not owned.

**Precedence rule**: content-validation checks run in the fixed order 409 → 415
→ 413. The first failing check in that order determines the single response
status for the whole request, and none of the files in the batch are stored
regardless of which file caused the failure (BR-30).

**GET /api/tickets/:ticketId/attachments/:attachmentId**
- 200 — metadata only (never the file body), including removed-state fields.
- 404 — not found or not owned.

**GET /api/tickets/:ticketId/attachments/:attachmentId/download**
- 200 — file stream, `Content-Type` from stored `mimeType`.
- 404 — not found, not owned, or the attachment is removed (BR-32).

**DELETE /api/tickets/:ticketId/attachments/:attachmentId**
Body: `{ reason?: string }` (≤200 chars).
- 200 — updated metadata with `isRemoved: true`, `removedAt`, `removalReason`.
- 404 — not found or not owned.
- 409 — already removed.

### Error response bodies

- 400 (validation failure): `{ errors: [{ field, message }] }` — one entry per
  invalid field, so the UI can place each message beside its control (§6).
- 403, 404, 409, 413, 415, 500: `{ error: string }` — a single safe, generic
  message; none of these originate from one specific form field, so none carry
  per-field detail.
  - 403 — `{ error: "Selected Requester is not active" }`.
  - 404 — `{ error: "Not found" }`, identical wording whether the resource is
    missing or owned by a different Requester (BR-10/BR-36).
  - 409 — `{ error: "Too many files in this request" }`,
    `{ error: "Attachment limit reached" }`, or
    `{ error: "Attachment already removed" }`, depending on which conflict
    occurred.
  - 413 — `{ error: "File exceeds 5 MB" }`.
  - 415 — `{ error: "Unsupported file type" }`.
  - 500 — `{ error: "Unexpected server error" }`; the real error is logged
    server-side only, matching the existing `/api/categories` handler pattern.

### HTTP status summary

| Status | Meaning in this API |
|---|---|
| 200 | Successful retrieval, or idempotent replay of a create |
| 201 | Resource created |
| 400 | Invalid input / field validation failure |
| 403 | `X-Requester-Id` does not match a currently active Requester |
| 404 | Resource missing, not owned by the caller, or removed (attachment download) |
| 409 | State conflict: attachment cap exceeded, >5 files in one request, double-removal |
| 413 | Uploaded file exceeds 5 MB |
| 415 | Uploaded file type not permitted |
| 500 | Unexpected server error; body never leaks internal detail |

## 9. Acceptance Criteria

- AC-01 Given valid Ticket data, when the Requester submits Create Ticket, then
  one Ticket is saved and the official Ticket Number is displayed.
- AC-02 Given no Development Requester is selected, when the user attempts to
  open My Tickets, then the Requester Selection screen is shown.
- AC-03 Given Requester B is selected, when a Ticket belonging to Requester A is
  requested by id, then no Ticket data is returned and the API responds 404.
- AC-04 Given the Summary field is left empty, when the Requester submits Create
  Ticket, then a field-level message appears under Summary and no API request is
  sent.
- AC-05 Given the same `Idempotency-Key` is sent twice on `POST /api/tickets`,
  when the second request arrives, then the original Ticket is returned and no
  second Ticket row exists.
- AC-06 Given the Requester clicks Submit while a request is already pending,
  when the second click occurs, then the Submit button is disabled and only one
  Ticket is created.
- AC-07 Given a Category has been deactivated since the form loaded, when the
  Requester submits Create Ticket referencing it, then the request is rejected
  with a 400 field-level error.
- AC-08 Given Ticket creation succeeds but the attachment upload fails, when the
  response returns, then the Ticket and its Ticket Number are shown and the
  failed attachment is reported with a retry option.
- AC-09 Given Requester A owns 25 Tickets, when Requester A opens My Tickets,
  then the list shows 10 Tickets per page with correct page-count metadata.
- AC-10 Given a search term matching part of a Ticket Number, when the Requester
  searches, then only matching Tickets are shown.
- AC-11 Given a Category filter is applied, when the filter is submitted, then
  only Tickets in that Category are shown.
- AC-12 Given a sort by Requested Priority is selected, when applied, then the
  list order reflects the chosen sort direction.
- AC-13 Given Requester C owns zero Tickets, when Requester C opens My Tickets,
  then the empty state (not the no-results state) is shown with a Create Ticket
  action.
- AC-14 Given Requester A has Tickets but none match the current filter, when the
  query returns zero rows, then the no-results state is shown with a Clear
  Filters action.
- AC-15 Given an owned Ticket with fewer than 5 active attachments, when the
  Requester uploads 1 valid file, then it appears as an active attachment.
- AC-16 Given an owned Ticket already at 5 active attachments, when the
  Requester attempts to add 1 more file, then the upload is rejected (409) and
  the existing 5 remain unchanged.
- AC-17 Given a single upload request contains 6 files, when submitted, then the
  entire request is rejected with 409 and none of the 6 files are stored.
- AC-18 Given a selected file exceeds 5 MB, when the Requester attempts to add
  it, then a client-side error is shown and no upload request is sent.
- AC-19 Given a selected file has an unsupported extension, when the Requester
  attempts to add it, then a client-side error is shown and, if bypassed, the
  server rejects it with 415.
- AC-20 Given an owned, active attachment, when the Requester clicks Remove and
  confirms, then it becomes non-downloadable and remains visible with its
  metadata.
- AC-21 Given a removed attachment's id, when any request attempts to download
  it, then the server returns 404 with no file content.
- AC-22 Given Requester A is viewing My Tickets, when the user switches to
  Requester B via Change Requester, then Requester A's tickets disappear and
  Requester B's tickets load.
- AC-23 Given the backend is unreachable, when the Requester submits Create
  Ticket, then a safe failure state is shown and all entered field values are
  preserved in the form.
- AC-24 Given a viewport under 768px, when My Tickets is open, then Tickets
  render as stacked cards with no horizontal page scrolling.
- AC-25 Given a keyboard-only user, when navigating the Development Requester
  Selection screen, then the dropdown and Continue button are reachable and
  operable via Tab/Enter with a visible focus indicator.
- AC-26 Given the seeded inactive Requester, when the Development Requester
  Selection screen loads, then that Requester does not appear in the dropdown.
- AC-27 Given a Development Requester is selected, when Create Ticket opens,
  then the Requester field displays that Requester as read-only, and the
  created Ticket row's `requesterId` matches the selected Requester's id.

## 11. Assumptions and Decisions

Meaningful choices not already fixed by the labsheet, each with its reason:

1. Requester context is transmitted as an `X-Requester-Id` header set by a thin
   API client wrapper on every request — keeps route bodies clean and is a
   drop-in replacement point for a real auth header in Lab 3.
2. Requester selection persists in `sessionStorage`, not `localStorage` — each
   new tab/session should require an explicit reselection rather than silently
   inheriting a stale test identity.
3. Duplicate-submission prevention is enforced two ways: a client-generated
   `Idempotency-Key` header with a DB-level unique constraint (authoritative),
   plus a disabled Submit button (first line of defense, immediate feedback).
4. `TicketStatus` ships with only `NEW` rather than the full set of statuses
   shown in the illustrative mockups — nothing in Lab 2 can produce any other
   value, and pre-populating unused enum members is speculative; Lab 3 extends
   the enum when the IT Staff workflow needs it.
5. IT Priority and Ticket Owner are omitted entirely, from schema through UI —
   the mockups illustrate the full multi-sprint product, but §4.2 explicitly
   excludes the IT Staff functions that would ever set or use either field, so
   storing or displaying them now would be dead data.
6. Attachment preview opens the active file directly in a new browser tab; no
   in-app thumbnail/embedded viewer is built — nothing in the spec requires an
   embedded viewer, and a new-tab open satisfies "inspect the attachment" at a
   fraction of the effort.
7. `Ticket` and `Attachment` share one migration — they ship in the same Issue
   and `Attachment` has a hard foreign-key dependency on `Ticket`, so splitting
   them into separate migrations would only add an intermediate broken state.
8. Cross-Requester access returns 404 (existence-hiding), not 403 — AC-03's
   wording ("the Ticket data is not returned") reads as denying existence, not
   merely denying access.
9. An upload batch is validated and stored atomically: any single failing file
   in a batch of ≤5 fails the whole request, matching the wholesale-rejection
   behavior explicitly required for batches of >5 files, rather than having two
   different partial/atomic behaviors depending on batch size.
10. My Tickets collapses to stacked cards (not a horizontally scrollable table)
    below 768px — sidesteps any risk of violating the "no horizontal page
    scrolling" rule that a scrollable table would risk.
11. Seed data includes ~25 / ~5 / 0 tickets across three active Requesters
    specifically so pagination, search, filtering, and both empty and
    no-results states are all demonstrable without manual data entry during
    grading.
12. `routing`: `react-router-dom` is added to the client — four-plus routed
    screens, a selector-guard redirect, and a Ticket-Detail deep link
